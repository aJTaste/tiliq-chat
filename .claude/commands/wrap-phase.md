このセッション（またはこの会話で完了した作業のまとまり）を「1つのPhase」として区切り、以下を順番に実行してください。**CLAUDE.md本体には実装詳細を一切書き足さないこと** — これは`tiliq-chat`プロジェクトが過去にCLAUDE.mdを1,477行まで肥大化させた失敗の再発防止のためのコマンドです。

## 手順

1. **Phase番号とスラッグを決める。** `CLAUDE.md`の「開発フェーズ」表を見て次の番号を採番し、内容を要約した短い英語スラッグ（例：`group-chat-m4`）を決める。既存の`docs/phases/phase-NN-slug.md`の命名パターンに合わせる。

2. **`docs/phases/phase-NN-slug.md`を新規作成する。** 既存ファイル（例：`docs/phases/phase-23-sidebar-redesign.md`）を1つ開いて構成を確認し、同じ見出し構造で書く：
   - `## Phase N の実装内容・詳細`
   - 概要（何を、なぜ）
   - 追加ファイル／変更ファイル／削除ファイル
   - DB変更（あれば。マイグレーション名も記録）
   - 設計判断・学び（**ここが一番重要**。次に似た作業をする将来のセッションが同じ調査・同じ失敗を繰り返さないための記録）
   - 検証方法・実施内容（`tsc`/`eslint`/ビルド/DB層検証など実際に行ったこと）
   - 動作確認してほしい項目（ユーザーによる実機確認が必要な場合）
   - 未対応・持ち越し事項（次のPhaseへの引き継ぎ）

3. **`CLAUDE.md`の「開発フェーズ」表に1行だけ追加する。** Phase番号・内容の1行要約・状態（完了/一部保留等）・`docs/phases/phase-NN-slug.md`へのリンク。**表以外の場所は変更しない。**

4. **`docs/backlog.md`を整理する：**
   - 今回のPhaseで解決した項目があれば、該当する行を削除する（経緯は`docs/phases/`側に残るので、取り消し線で残す必要は無い）
   - 今回新たに判明した持ち越し事項・要望があれば、適切なセクションに追記する

5. **該当すれば以下も更新する：**
   - ファイル構成やアーキテクチャ上のパターンが変わった → `docs/architecture.md`
   - Phase横断で使える技術的教訓（Next.js/Postgres/RLS/Realtime/依存関係更新など）が新たに判明した → `docs/lessons.md`
   - `docs/srs.md`との乖離が生じた → `docs/srs.md`に実態を注記（既存の`lock_type`/`lock_secret`注記と同じパターン）

6. **`docs/backlog.md`・`CLAUDE.md`・関連ファイルの行数が想定より膨らんでいないか軽く確認する。** `docs/backlog.md`が肥大化してきたら、古い・優先度不明な項目を思い切って削除するか、ユーザーに要否を確認する。

7. **最後にユーザーへ変更内容を要約し、コミットしてよいか確認する。** 問題なければConventional Commits形式でコミットする（`git add` → `git commit -m "..."`。既存のコミット履歴の書式・Phase番号の書き方に合わせる）。

## 注意

- 1つのPhaseが小規模（コード変更なし・調査のみ等）でも、記録価値があるなら`docs/phases/`への短いファイル作成は省略しない（例：Phase 15・20は「コード変更なし」の調査回だが、次回同じ調査を繰り返さないための記録として価値があった）
- 逆に、些細な追加コミット（同一Phase内の追加修正）は既存の`docs/phases/phase-NN-*.md`に追記すればよく、新しいPhase番号を無理に採番する必要はない
